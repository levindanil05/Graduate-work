# Архитектура: documents (ядро), plans (PLX-фасад), external_sync (внешние хранилища)

Документ фиксирует границу приложений, слоты компаньонов и связи `DocumentRelation`.  
Связанное ТЗ: [planing-2605010.md](planing-2605010.md) §10.2.  
Внешние облака и зеркала: [external-storage-sync.md](external-storage-sync.md).  
Реестр видов, профили жизненного цикла и слоты: [configurable-document-types.md](configurable-document-types.md).

---

## 1. Граница apps

| Слой | Роль | Примеры |
|------|------|---------|
| **documents** | Универсальное ядро | `Document`, `DocumentVersion`, Alias, Workflow, Discussion, `DocumentRelation`; порты storage / hash / naming / extractor; указатель утверждённой версии; поставщик профиля жизненного цикла |
| **plans** | PLX-фасад (тип «учебный план») | список и фильтры УП, upload PLX, parser, канонические имена, abbr dict, `PlacementPolicy` (раскладка по папкам УО); карточка с блоком слотов компаньонов |
| **external_sync** | Согласование с внешними хранилищами | подключения, checkpoint, привязки реплик, запуски, исходящие намерения, рубильники, адаптер Яндекс.Диска |

### Правила

1. Новые виды документов живут в той же системе `documents` (свой `document_type` + при необходимости тонкий UI-модуль рядом с `plans`).
2. PLX-специфику **не** переносить в ядро `documents` (включая правила папок факультетов/архива на Яндекс.Диске — это `PlacementPolicy` в `plans`).
3. Legacy-модель `EducationalPlan` удалена (миграция `plans.0008_remove_educationalplan`). Данные УП — только `Document` / `DocumentVersion`.
4. Облачные SDK, OAuth и обход внешних каталогов живут в `external_sync`, не в `documents`. Изменения версий извне — только через прикладные операции ядра (доверенный импорт / публикация), не прямой записью ORM.
5. Клиент `plans.yandex_client` и команда `update_from_yandex` — прототип односторонней загрузки; целевая реализация — адаптер и согласователь в `external_sync` ([external-storage-sync.md](external-storage-sync.md)).

### Имя типа учебного плана

| В ТЗ (исторически) | В коде | Смысл |
|--------------------|--------|--------|
| `study_plan` | **`plx`** | Учебный план в формате PLX |

Код `plx` = учебный план (PLX). Переименовывать enum не требуется; в UI пользователю показывается «Учебный план», не идентификатор типа.

```text
external_sync  ── внешние подключения, согласование, рубильники, отчёт запусков
       │ вызывает
documents      ── универсальные операции (версия, статус, обсуждение, хранение, связи)
       ▲
       │ использует
plans          ── UI и логика именно для document_type = plx, PlacementPolicy
```

### PlacementPolicy и внешние копии

Раскладка файлов по папкам учебного отдела (факультет, форма обучения, кафедра, `Архив`) — PLX-специфика: живёт в `plans` как `PlacementPolicy`. Согласователь в `external_sync` спрашивает политику «роль пути / куда положить / как назвать архив», но не содержит словаря аббревиатур и не разбирает PLX.

Копия на Яндекс.Диске — `ExternalReplica` версии, не `DocumentRelation` и не `DocumentAlias`. Подробности моделей, рубильников и алгоритма: [external-storage-sync.md](external-storage-sync.md).

## 2. Компаньоны и слоты

Компаньон — обычные `Document` / `DocumentVersion` своего вида. В списке учебных планов его нет. На карточке главного документа он в блоке слотов. Отдельный срез реестра по виду показывает сами компаньоны; с карточки компаньона есть переход к главному документу.

Состав слотов **не** зашит в код: у вида в `DOCUMENT_TYPES` список `companions`. Главным может быть документ любого вида, не только `plx`. Связь — ребро «компаньон → главный»; цепочка длиннее двух уровней в данных допустима. В интерфейсе этого этапа — один уровень: слоты главного и обратная ссылка. Сервис запрещает цикл.

### 2.1. Первый слот: печатная форма

| | |
|--|--|
| **Суть** | Печатная форма учебного плана (раньше чаще PDF/прежний печатный вид, сейчас чаще Excel). Один вид документа, не два. |
| **`document_type`** | `printed_form` |
| **Якорь** | **Редакция** УП (`edition`) |
| **Расширения** | `.pdf`, `.xlsx` |
| **Жизненный цикл** | Короткий: «Черновик» → «Утверждён». Без проверки и согласования. Ведёт учебный отдел; разработчик УП только скачивает. |
| **Перепривязка** | Существующую форму можно перенести на другую редакцию того же плана без нового файла (незначительные правки PLX). |
| **Генератор** | Позже: авточерновик из PLX. Сейчас ключ генератора пустой. |

ОПОП/ПООП и zip с РПД/практиками в реестр **не** записываем. Их добавление — новая запись вида и строка в `companions` у главного вида.

```mermaid
flowchart LR
  Primary[Document любого вида]
  Edition[DocumentVersion]
  Companion[Document компаньона]
  Draft[Редакция черновик]
  Signed[Редакция с подписью]
  Primary --> Edition
  Edition -->|"anchor edition"| Companion
  Primary -->|"anchor document"| Companion
  Companion --> Draft
  Companion --> Signed
```

## 3. DocumentRelation

| Поле | Смысл |
|------|--------|
| `source_document` | Компаньон (всегда есть) |
| `target_document` | Главный документ; **всегда заполнен** |
| `target_version` | Редакция-якорь; для `edition` обязательна, для `document` = `NULL` |
| `slot_code` | Код вида компаньона из слота (`printed_form`) |
| `is_current` | Действующая связь этого слота на данном якоре |

Инварианты:

- связь всегда хранит `target_document`;
- для якоря `edition` обязателен `target_version`;
- для якоря `document` `target_version` = `NULL`;
- кратность (например `0..1`) проверяется сервисом при привязке и перепривязке.

### Политики

1. **Перепривязка** — перенос текущей связи на другую редакцию того же главного; файл не меняется.
2. **Удаление главного** — спрашиваем, удалять ли прямых зависимых. По умолчанию нет: связи снимаются, компаньоны становятся сиротами. Согласие удаляет только прямых зависимых при наличии права.
3. **Сироты** — в срезе реестра фильтр «без главного» и массовое удаление отмеченных.
4. **Approve PLX** — для слотов с якорем `edition` автоматически ничего не делаем в этой версии (перепривязку выполняет пользователь).

### Что не смешивать

| Механизм | Назначение |
|----------|------------|
| `DocumentAlias` | Идентичность **одного** документа (имена файлов / алиасы) |
| `documents.relationship_map` | Целостность внутренних ссылок (version↔document) |
| `DocumentRelation` | Связи между разными документами / версиями |
| `ExternalReplica` (`external_sync`) | Копия **той же** версии во внешнем каталоге |

## 4. Профиль жизненного цикла

Жизненный цикл — данные профиля вида, не общая таблица в коде. Рантайм спрашивает профиль у **поставщика**. В этой версии поставщик читает `DOCUMENT_TYPES` / встроенный профиль плана. Позже тот же контракт читает таблицы в БД (конструктор в админке без перезапуска).

Колонка `DocumentVersion.status` и поле действия перехода — строки **без** закрытого списка `choices`, чтобы уникальные коды статусов можно было записывать без миграции.

Корзина, восстановление и окончательное удаление — системные действия, в конструктор цикла не входят.

Подробности полей профиля и слотов: [configurable-document-types.md](configurable-document-types.md).
