# HOWTO: подключение Яндекс.Диска

Практическая инструкция: как получить OAuth-токен, указать путь к папке и включить два подключения (`uo_readonly` и `mike_rw`).

Архитектура и алгоритм согласования: [external-storage-sync.md](external-storage-sync.md). Пример переменных: [`src/education_site/.env.example`](../src/education_site/.env.example).

---

## 1. Что понадобится

Два независимых сценария (можно настроить по очереди):

| Подключение | Код (`slug`) | Назначение | Права на Диске |
|-------------|--------------|------------|----------------|
| Папка УО | `uo_readonly` | Только получать изменения (импорт / мониторинг) | Чтение (достаточно доступа «на просмотр» к чужой папке) |
| Копия Mike | `mike_rw` | Получать и отправлять утверждённые версии | Чтение и запись на **вашем** диске |

Одновременно «получать изменения» (`pull_enabled`) можно включить **только у одного** подключения. Push разрешён только у `mike_rw`.

Токен **не** хранится в БД. В подключении указан `credential_ref` — имя переменной окружения. Сам секрет — в файле `.env` рядом с `manage.py` (или в окружении процесса).

## 2. Получение OAuth-токена

### 2.1. Создать приложение

1. Откройте [https://oauth.yandex.ru/](https://oauth.yandex.ru/) и войдите в Яндекс-аккаунт, от имени которого будет ходить API.
2. Создайте приложение (тип — для доступа к API / веб-сервисам; точное название пункта в интерфейсе может меняться).
3. В правах доступа отметьте **Яндекс.Диск**:
   - для `uo_readonly`: достаточно **чтения** (`cloud_api:disk.read`);
   - для `mike_rw`: **чтение и запись** (`cloud_api:disk.read` + `cloud_api:disk.write`).
4. Сохраните приложение и скопируйте **ClientID** (и при необходимости Client secret — для кода обмена, если используете полный OAuth-flow).

Права только на «папку приложения» недостаточно, если каталог УО лежит в произвольном месте Диска: нужен доступ ко всему диску (или к тем сегментам, куда реально ведёт путь).

### 2.2. Выпустить токен

Удобный способ для локальной разработки и стенда — debug-токен через форму Яндекса:

1. Откройте страницу вида  
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENT_ID`
2. Подтвердите доступ под нужным аккаунтом.
3. После редиректа в адресной строке будет фрагмент `#access_token=...&token_type=bearer&...`. Скопируйте значение `access_token` (до следующего `&`).

Альтернатива: обмен `code` на токен по документации OAuth Яндекса — если настраиваете продакшен-приложение с redirect URI.

Для **папки УО (только чтение)** токен должен быть выпущен от аккаунта, у которого есть доступ к этой папке (владелец или расшаренный доступ «на просмотр»).  
Для **копии Mike** — токен вашего аккаунта, где лежит копия с правом записи.

Не коммитьте токен в git и не вставляйте его в код. Не логируйте его.

### 2.3. Проверка токена (опционально)

В Python с установленным `yadisk`:

```python
import yadisk
disk = yadisk.YaDisk(token="ВАШ_ТОКЕН")
print(disk.check_token())  # True, если токен жив
print(list(disk.listdir("/")))  # или ваш root_path
```

## 3. Как указать путь к папке

Путь — **posix-путь от корня Диска**, как в веб-интерфейсе, без префикса `disk:`.

Примеры:

- `/` — весь диск (обычно слишком широко);
- `/Учебный отдел/Планы` — папка УО;
- `/Планы-копия` — ваша рабочая копия.

Правила:

- начинайте с `/`;
- используйте `/`, не `\`;
- имя папки должно совпадать с тем, что на Диске (регистр и пробелы важны);
- система обходит корень рекурсивно; роль «архив» определяется по сегменту пути `Архив` / `АРХИВ` (без учёта регистра) — см. [external-storage-sync.md](external-storage-sync.md).

Путь задаётся **дважды согласованно**:

1. в `.env` — `YANDEX_DISK_*_BASE_PATH` (документирование / запасной ориентир);
2. в Admin у подключения — поле **«Корневой путь»** (`root_path`) — **именно его** использует провайдер при обходе.

После смены пути в Admin сохраните подключение и сделайте пробный прогон.

## 4. Настройка `.env`

Скопируйте пример и заполните:

```bash
cp src/education_site/.env.example src/education_site/.env
```

Минимум для двух подключений:

```env
YANDEX_DISK_UO_READONLY_TOKEN="y0_AgAAAA..."
YANDEX_DISK_UO_READONLY_BASE_PATH="/путь/к/папке/УО"

YANDEX_DISK_MIKE_RW_TOKEN="y0_AgAAAA..."
YANDEX_DISK_MIKE_RW_BASE_PATH="/путь/к/вашей/копии"
```

| Переменная | Для какого `credential_ref` |
|------------|-----------------------------|
| `YANDEX_DISK_UO_READONLY_TOKEN` | подключение `uo_readonly` |
| `YANDEX_DISK_MIKE_RW_TOKEN` | подключение `mike_rw` |

Устаревшие `YANDEX_DISK_TOKEN` / `YANDEX_DISK_BASE_PATH` оставлены только для старого прототипа; для новых подключений их не используйте.

Перезапустите процесс Django (или shell), чтобы подтянуть `.env`.

## 5. Настройка в Django Admin

1. Войдите как администратор → **Внешняя синхронизация**.
2. **Настройки внешней синхронизации**: включите «Внешняя синхронизация» (`external_sync_enabled`).
3. **Внешние подключения** — записи уже созданы миграцией:

### `uo_readonly` — Яндекс.Диск УО (только просмотр)

- Режим доступа: только чтение (`push` принудительно выкл).
- Ссылка на секрет: `YANDEX_DISK_UO_READONLY_TOKEN`.
- Корневой путь: тот же, что в `YANDEX_DISK_UO_READONLY_BASE_PATH`.
- Для первичного импорта: **Получать изменения** = вкл; у `mike_rw` при этом pull выкл.

### `mike_rw` — копия с записью

- Режим: чтение и запись.
- Ссылка на секрет: `YANDEX_DISK_MIKE_RW_TOKEN`.
- Корневой путь: путь к копии.
- Когда работаете с этой копией: pull на `uo_readonly` выкл; на `mike_rw` — **Получать изменения** и при необходимости **Отправлять утверждённые версии**.

Роли с доступом к экрану синхронизации: **управляющий** и **администратор**.

## 6. Первый запуск

Рекомендуемый порядок:

1. Заполнить токен и путь только для `uo_readonly`.
2. Включить глобальный рубильник и `pull_enabled` у `uo_readonly`.
3. Запустить получение изменений одним из способов:
   - UI: список планов → **Синхронизация с внешним хранилищем** → выбрать подключение → «Запустить получение изменений»;
   - команда:
     ```text
     python manage.py sync_external_storage --connection=uo_readonly
     ```
4. Просмотреть отчёт прогона (счётчики, строки «требует обработки»).
5. Повторный запуск без изменений на Диске должен дать почти нулевой импорт (идемпотентность).
6. Переключить мониторинг на `mike_rw` (и при необходимости включить отправку), когда будете публиковать утверждённые планы на свою копию — **не** на папку УО с доступом только на чтение.

Флаги команды:

- `--pull-only` — только получение;
- `--push-only` — только накопленные исходящие намерения (имеет смысл для `mike_rw` при включённом push).

## 7. Типичные ошибки

| Симптом | Что проверить |
|---------|----------------|
| «Не задан токен» / «Неверный токен» | Имя в `.env` = `credential_ref`; токен без лишних кавычек/пробелов; `check_token()`; процесс перезапущен |
| Пустая выгрузка / 0 файлов | `root_path` совпадает с реальной папкой; в папке есть `.plx`; у аккаунта есть доступ к расшаренной папке |
| Ошибка записи / Read-only | Push на `uo_readonly` запрещён; для записи используйте `mike_rw` и токен с `disk.write` |
| «Другой прогон уже выполняется» | Дождитесь окончания или истечения lease у подключения |
| Не включается pull у второго облака | Сначала выключите «Получать изменения» у другого подключения |

---

## 8. Безопасность (кратко)

- Токены только в env / secret store, не в репозитории.
- Не логировать токены и URL с query-секретами.
- Для боевой папки УО сначала dry-run на копии каталога и read-only подключении.
- Локальная работа с планами (загрузка, workflow) не зависит от включённой синхронизации; при выключенном push утверждение не блокируется.
